# 个人影音库 2.0：源码审查与实施清单

审查基线：`df85893`

## 一、现有架构与功能边界

当前项目由三层组成：

1. C# WinForms + WebView2 桌面外壳启动内嵌 Python 服务。
2. Python 标准库 HTTP 服务读取 `02-电影阅读/**/*.md`，提供媒体库、搜索、导入、编辑、删除、封面修复和批量游戏升级接口。
3. 原生 HTML/CSS/JavaScript 负责海报墙、筛选、排序、详情编辑和豆瓣导入。

Markdown frontmatter 是当前唯一正式数据源。媒体类型由 `type` 字段决定，缺失时回退到父目录名；当前数据包含 `movie`、`teleplay`、`game`、`book` 四类，共 292 篇。封面共 291 个本地引用，均有对应文件；另有 1 个远程地址。

现有 API、字段和主要功能将在 2.0 中保留。升级后的缓存、备份、修订号和规范化模型只作为辅助或兼容层，不取代 Markdown。

## 二、必须在第一阶段修复的数据安全问题

### P0：切换详情后延迟保存到错误笔记

评价输入框有 700ms 防抖。回调调用全局 `save()`，而 `save()` 在回调实际触发时才读取全局 `current.path`。如果用户输入后立刻关闭详情并打开另一条媒体，上一条评价可能写入下一条笔记。

处理：

- 保存请求显式绑定已捕获的笔记路径和修订号。
- 关闭详情、切换详情和输入框失焦时立即提交该条笔记的待保存评价。
- 每个笔记使用独立保存队列，避免连续修改乱序落盘；旧响应不得覆盖新响应。

### P0：整文件直接覆盖，缺少原子写入和回滚

`Library.update()`、`fix_image()`、新建笔记和附件写入均直接调用 `write_bytes()` 或文件句柄覆盖。进程被结束、磁盘写入失败或代码异常时可能留下半写文件。

处理：

- 写前严格以 UTF-8 解码；遇到非法 UTF-8 停止写入，不再用替换字符静默破坏内容。
- 在同一目录写临时文件、刷新到磁盘，再用 `os.replace()` 原子替换。
- 每次修改已有笔记前，在 Vault 的 `.media-app/backups/notes/` 保存原文；封面替换前也保存原图。
- 写入后重新解析并验证目标字段；失败时恢复备份。
- 保留原换行风格、末尾换行和 BOM 状态。

### P0：外部编辑与并发保存可能互相覆盖

后端虽然持有 `RLock`，但没有覆盖读文件的整个修改过程，也没有检测 Obsidian 在读取后修改了文件。两个前端请求也可能基于同一旧内容先后覆盖。

处理：

- 对笔记按路径加锁，覆盖“读取、修改、备份、写入、校验”全过程。
- 返回文件修订号；保存时校验修订号，发现外部变化则拒绝覆盖并返回最新内容。
- 前端明确提示“笔记已在 Obsidian 中变化，请确认后重试”。

### P1：修改和删除的路径范围过宽

当前只校验目标位于 Vault 内。API 可以尝试移动 Vault 内任意文件，而不限于 `02-电影阅读/` 下 Markdown 文件。

处理：

- 编辑、删除和封面修复只允许 `02-电影阅读/` 内的 `.md` 文件。
- 本地封面只允许解析到 Vault 的 `attachments/`。
- 继续拒绝目录穿越和符号链接逃逸。

### P1：缓存不能感知 Obsidian 外部编辑

服务启动后 `LIB.snapshot()` 一直返回内存快照，只有手动点击刷新才重新读取；外部修改后详情页可能显示旧状态。

处理：

- 每次读取媒体列表时检查 Markdown 文件签名，只重读发生变化的文件。
- 前端在窗口重新获得焦点时自动刷新；保存遇到修订冲突时同步最新内容。

### P1：封面覆盖可能影响其他引用，且图片校验不完整

修复封面时会原地覆盖同名附件。将来若多篇笔记共用封面，会同时改变其他笔记。新建时的 data URL 也没有在落盘前完整校验魔数。

处理：

- 已有附件默认写新版本并通过原子替换更新当前笔记，不原地覆盖可能被共用的文件。
- data URL 解码后验证图片魔数和大小，并先写临时文件再启用。
- 清理本次操作明确创建但最终未使用的附件。

### P1：进程退出可能中断正在进行的写入

窗口关闭时直接执行 `taskkill /T /F`。另外，窗口外壳只根据端口返回内容中出现 `true` 就认定是影音库服务，可能连接到其他本地服务。

处理：

- 服务提供带实例标识的 ping 和受控退出。
- 外壳先请求正常退出并等待；超时后才结束自己启动的进程树。
- 保留“复用已运行服务”的能力，但只复认同版本影音库实例。

### P1：保存失败后前端保留错误状态

状态、个人评分等控件会先改前端数据，再异步保存；失败时没有恢复原值，也没有处理乱序响应。

处理：

- 统一保存队列在成功后提交新快照；失败时恢复控件和列表数据。
- 校验 HTTP 状态与 JSON 响应，网络错误、冲突和服务器错误给出明确提示。

## 三、第二阶段：统一数据模型与兼容迁移

### 当前差异

- 媒体类型统一，但所有者字段随类型变化：`director`、`author`、`publisher`。
- 题材同时存在 `tags` 与游戏专用 `genre`。
- `score` 在其他类型为 10 分制，在游戏通常为 Metacritic 0–100；现有库中有 2 个旧游戏使用 10 分制。
- `status` 是通用布尔值，但正文文案随类型变化，书籍目前没有稳定的读写文案。
- 标题简称、简介、完成时间和封面只在部分旧笔记中存在；旧游戏有 43 篇没有正文看板。
- `scoreStar`、`currentDate`、`imageDataurl`、`dateModified` 是历史附加字段。

### 兼容方案

- Markdown 继续使用现有字段作为正式存储，不重命名路径、标题、正文或已有字段。
- 在服务端建立唯一规范化入口，向新旧前端同时返回：
  - 保留的旧字段：`type`、`score`、`myScore`、`status`、`image` 等。
  - 规范化字段：`schemaVersion`、`mediaType`、`rating`、`personalScore`、`statusValue`、`completedAt`、`tags`、`creators`、`description`。
- 统一读取别名：
  - 类型别名和缺失类型回退父目录。
  - `tags` + `genre` 合并去重。
  - `director` / `author` / `publisher` 统一映射为创作者。
  - 日期接受日期、年月、纯年份以及带地区后缀的旧值。
  - 旧游戏 ≤10 分按 10 分制解释；高分为 100 分制，同时在规范化结果中提供换算后的 10 分制值。
- 写入仍使用原字段，避免破坏在 Obsidian 中直接查看和 Dataview 查询。
- 为新建条目写入 `schemaVersion: 2`；旧条目按需兼容读取，不强制批量加字段。
- 提供 `--audit-library` 和 `--migrate-library --dry-run`。正式迁移先备份；只补充确实需要的兼容字段，不删除历史字段。

## 四、实施与验收顺序

### 第一阶段提交

1. 路径约束、严格 UTF-8、按笔记锁、修订号、备份、原子写入和回滚。
2. 前端目标路径绑定、保存队列、关闭时提交、冲突处理和失败恢复。
3. 封面安全写入、外部编辑刷新、服务身份校验和受控退出。
4. 回归测试：
   - 292 篇现有笔记全部可解析，字段与封面检查无新增异常。
   - LF、CRLF、无末尾换行三种文件写入后保持原格式。
   - 正文除目标 Callout 行外逐字节不变。
   - 保存失败、备份、回滚、外部修改冲突、越界路径均有测试。
   - 切换详情后的评价不会跨笔记写入。
   - 现有搜索、筛选、导入、状态、评分、个人评价、游戏信息、封面和删除流程不变。

### 第二阶段提交

1. 规范化模型与旧字段兼容层。
2. 审计和 dry-run 迁移工具。
3. 前端改用规范化评分、状态、标签和创作者字段，同时继续接受旧 API 字段。
4. 回归测试：
   - 现有 292 篇在前端显示数量、类型、标题、年份、标签、评分和状态与升级前一致。
   - 两种旧游戏评分都可正确显示和排序。
   - `tags` 与 `genre`、三类创作者字段、缺失类型和不同日期格式均能读取。
   - 迁移 dry-run 不改文件，正式迁移有备份且可重复执行。

## 五、暂不做的事

- 不引入数据库、前端框架或新第三方运行时依赖。
- 不改现有文件名、目录结构、Obsidian 链接和正文主体。
- 不把缓存或备份作为唯一数据源。
- 不直接对当前 Vault 执行批量迁移；部署构建和迁移均先使用临时副本验证。
